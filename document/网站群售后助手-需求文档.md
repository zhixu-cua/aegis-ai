# 网站群售后助手需求文档

## 1. 文档信息

- 项目名称：网站群售后助手
- 项目定位：面向网站群运营、实施、售后人员的独立部署式 AI 售后助手系统
- 交付目标：由个人开发者在有限周期内完成一个可上线试运行的 MVP 版本
- 集成方式：网站群后台增加菜单入口，跳转访问独立助手系统
- 当前范围：方案一，仅做通用知识库问答，不做工单闭环

## 2. 项目背景

网站群售后场景中，常见问题具有明显的重复性，例如栏目发布失败、模板显示异常、附件访问问题、登录权限问题、静态页生成异常、站点配置项不生效等。售后人员往往需要频繁查阅历史文档、部署手册、FAQ、运维说明和经验记录，才能给出相对准确的处理建议。

现有处理方式存在以下问题：

- 问题处理依赖经验，人员差异较大
- 知识分散在文档、聊天记录、历史案例中，不易快速检索
- 回复内容口径不统一，容易遗漏操作步骤
- 新人培养周期长，常见问题重复回答效率低

因此需要建设一个独立部署的售后助手系统，通过与网站群解耦的方式优先解决“快速问答”和“标准化回复建议”问题，在尽量不影响网站群原始代码的前提下实现快速落地。

## 3. 产品目标

### 3.1 总体目标

建设一个面向网站群体系的独立售后问答系统，通过统一知识库为运营和售后人员提供：

- 常见问题快速问答
- 标准化处理建议输出
- 引用来源可追溯
- 低置信度时明确提示转人工
- 与网站群主系统解耦的独立运行能力

### 3.2 MVP 目标

MVP 阶段聚焦以下目标：

- 在现有后台中提供一个可用的问答入口
- 支持通过网站群后台菜单跳转进入独立系统
- 支持上传售后知识文档并建立知识库
- 支持基于知识库的检索增强问答
- 支持返回引用来源
- 支持记录问答日志与操作审计

### 3.3 非目标

以下内容不在本期范围内：

- 按站点维度隔离知识库
- 自动生成或流转工单
- 自动执行后台写操作
- 接入企业微信、邮件、电话转写等多渠道
- 自动同步 CMS 栏目或文章内容

## 4. 目标用户

### 4.1 售后人员

主要使用系统进行日常问题咨询、处理建议获取和回复内容整理。

### 4.2 网站运营人员

在后台处理站点配置、栏目、文章、模板、附件等问题时，使用助手快速获取说明和排查步骤。

### 4.3 管理员

负责知识库文档维护、问答日志查看和基础参数配置。

## 5. 使用场景

### 5.1 常见问题快速咨询

用户在后台提问，例如：

- “为什么文章发布后前台看不到？”
- “附件上传成功但访问 404 怎么排查？”
- “栏目模板修改后没有生效的常见原因是什么？”

系统根据知识库返回明确结论、排查顺序和引用来源。

### 5.2 标准回复生成

售后人员在获得答案后，可直接复制系统生成的标准化回复，用于工单答复、电话记录补录或即时沟通。

### 5.3 新人辅助学习

新接手网站群售后的人员，可通过系统快速了解常见问题的定位方法，降低培训成本。

### 5.4 知识沉淀与复用

管理员将操作手册、FAQ、实施交付说明、常见故障处理文档上传入库，形成持续可复用的知识资产。

## 6. 功能范围

### 6.1 独立系统接入

系统应以独立 Web 系统形式提供问答能力，网站群后台仅增加一个菜单或入口链接，点击后跳转进入助手系统。独立系统至少包含：

- 提问输入框
- 问答结果展示区
- 引用来源展示区
- 历史会话列表
- 复制回复按钮

网站群侧本期要求控制在最小范围，原则上不修改核心业务代码，仅增加访问入口。

### 6.2 知识库管理

管理员应可在后台维护通用知识库，支持：

- 上传文档
- 查看文档列表
- 删除文档
- 重建索引
- 查看入库状态

MVP 支持手工上传文档，不要求自动同步站点内容。

### 6.3 检索增强问答

系统应对用户问题执行知识检索，并在回答时使用检索结果增强模型输出，避免纯模型臆造。

回答应满足：

- 优先给出明确结论
- 给出建议排查步骤
- 显示引用来源
- 在依据不足时明确说明不确定

### 6.4 问答日志与审计

系统应记录以下信息：

- 提问人
- 提问内容
- 回答摘要
- 是否命中知识库
- 使用了哪些引用来源
- 处理耗时
- 时间戳

### 6.5 后续扩展预留

虽然 MVP 不做工单流转，但系统接口与数据结构应预留以下扩展能力：

- 人工转工单
- 工单状态跟踪
- 渠道消息接入
- 站点维度知识隔离

## 7. 核心业务规则

- 知识库为全站通用，不区分站点使用不同知识库
- 所有问答均以知识库检索结果为主要依据
- 当检索结果不足以支撑回答时，系统必须提示“建议人工处理或补充信息”
- 系统输出仅作为售后辅助建议，不直接执行后台写操作
- 文档删除后，对应知识切片与向量数据必须同步失效

## 8. 典型用户流程

### 8.1 问答流程

1. 售后人员进入网站群后台
2. 点击“售后助手”菜单，跳转到独立系统
3. 在独立系统中输入问题并提交
4. 系统检索知识库并生成回答
5. 页面展示答案、引用来源、是否建议人工处理
6. 用户复制回复或继续追问

### 8.2 文档入库流程

1. 管理员进入知识库管理页面
2. 上传 PDF、Word、Markdown、HTML 或 TXT 文档
3. 系统完成解析、切分、向量化和入库
4. 文档状态变为“可检索”
5. 后续问答可使用该文档内容

## 9. 页面需求

### 9.1 售后助手页面

建议采用独立门户页面布局，页面元素包括：

- 会话列表
- 当前问题输入区
- 回答展示卡片
- 引用来源折叠区
- 复制回复按钮
- “没有解决，建议转人工”提示

### 9.2 知识库管理页面

页面至少包括：

- 文档上传入口
- 文档列表
- 文档状态
- 文档删除
- 索引重建按钮

## 10. 非功能需求

### 10.1 易部署

- 支持单机 Docker Compose 部署
- 组件数量尽量精简，便于个人维护
- 不依赖网站群主工程重新打包发布
- 支持 Windows 本地开发与调试
- 支持后续迁移到 Linux 服务器部署
- 配置、脚本与路径设计尽量避免依赖 Windows 绝对路径

### 10.2 可维护

- Java 业务层与 AI 服务边界清晰
- 各组件可单独替换和扩展
- 开发环境与生产环境差异应主要收敛在配置层，而不是代码层

### 10.3 性能目标

- 常规问答接口响应时间目标：5 到 15 秒
- 文档上传后的解析和入库允许异步处理

### 10.4 安全要求

- 网站群与助手系统之间采用菜单跳转方式接入
- 首期可采用独立登录，后续可扩展单点登录或票据透传
- 接口访问需经过权限校验
- 日志中避免明文记录敏感信息
- AI 服务不直接暴露给未授权前端调用

## 11. 成功标准

MVP 验收可按以下标准执行：

- 可在后台正常发起问答
- 网站群可通过菜单入口稳定跳转到助手系统
- 至少可上传并检索常见售后知识文档
- 回答中可展示引用来源
- 无依据时能明确拒答或提示人工处理
- 管理员可查看知识库和问答日志

## 12. 实施优先级

### P0

- 后台问答页面
- 文档上传与入库
- 检索增强问答
- 引用来源展示
- 问答日志

### P1

- 会话历史
- 常见问题推荐
- 用户反馈“有帮助/无帮助”

### P2

- 工单联动
- 多渠道接入
- 站点级知识隔离
- 自动同步 CMS 内容

## 13. 单人交付计划

### 第 1 阶段：基础打通

- 完成独立问答门户
- 完成网站群菜单跳转入口
- 完成 Spring Boot 与 FastAPI 通信
- 完成模型调用能力

### 第 2 阶段：知识库能力

- 完成文档上传
- 完成文本解析、切分、向量化
- 完成基于 pgvector 的检索

### 第 3 阶段：可用性补齐

- 增加引用来源展示
- 增加拒答兜底逻辑
- 增加问答日志与基础审计

### 第 4 阶段：管理能力

- 补全文档管理页
- 增加入库状态、删除和重建索引

### 时间预估

- MVP 开发周期：2 到 4 周
- 前提条件：Windows 开发机可运行 Docker Desktop，后续 Linux 服务器具备 Docker Engine 或 Docker Compose 环境

## 14. 风险与应对

- 文档质量不高导致回答不准
  - 应对：优先整理高质量 FAQ 和处理手册
- 本地模型效果不稳定
  - 应对：通过提示词模板、检索约束和引用机制降低幻觉
- 文档解析效果不一致
  - 应对：首期优先支持结构较稳定的格式，并保留人工修订机制
- 个人开发时间有限
  - 应对：严格控制 MVP 范围，仅做问答闭环
